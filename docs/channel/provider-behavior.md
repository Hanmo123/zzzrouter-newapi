# 服务商、渠道评测与价格行为约定

本文记录当前已生效的行为，以及“每个渠道的每个模型独立定价”的需求边界。**待确认的价格方案不是已实现功能，也不会因为本文新增而改变实际扣费或路由。**

详细 API、迁移与实现说明见 [PROVIDERS.md](../../PROVIDERS.md)。

## 1. 实现状态

| 能力 | 状态 | 行为 |
| --- | --- | --- |
| 服务商与渠道关联 | 已实现 | 一个服务商可包含多个渠道，凭据和协议配置仍属于渠道 |
| 渠道上游倍率 `upstream_ratio` | 已实现 | 用于 `floor` 排序与 `multiplier` 筛选，不直接参与用户扣费 |
| 渠道公开倍率 `public_ratio` | 已实现 | 用于公开展示和实际用户计费，与上游倍率独立 |
| 系统模型价格 | 已实现 | 沿用系统模型计费配置，可包含 token 计费、固定价或计费表达式；不是自动实时同步的官方报价 |
| 渠道 × 模型独立价格 | **尚未实现，口径待确认** | 当前没有可以配置并生效的逐渠道模型单价，不应把它描述为已有管理字段或 API |
| 逐次渠道评测历史 | 已实现 | 主库追加保存真实结果，独立于可清理的系统任务及消费日志 |
| 公开服务商历史页面 | 已实现 | 展示 TTFT、按检测样本计算的可调用情况和最近记录 |
| ClickHouse 评测写入 | **尚未实现** | 已隔离存储契约，未来通过事务 outbox 异步镜像，不在主库事务内远程双写 |

## 2. 三类价格概念不能混用

### 系统模型计费配置

这是当前用户费用计算的模型基础。输入、输出、缓存等用量按照现有模型配置计算；表达式和固定价遵循各自的既有计费方式。

“回退系统模型价”不等于“实时读取官方价格”：管理员可能已修改系统价，内置参考价格也不承诺自动跟随厂商变动。

### 上游采购价格与倍率

上游采购价表示服务商收取运营方的成本。当前只保存渠道级 `upstream_ratio`，**没有保存逐渠道、逐模型的倍率前采购基础价**。

倍率是无量纲数，不能单独表达美元单价、币种、输入/输出差价、缓存优惠或阶梯价格。只有基准价和单位对齐时，不同渠道的倍率才可以直接作为成本比较依据。

### 用户计费基础价与公开倍率

用户计费基础价是用于向用户收取费用的模型价格；它不必等于采购价。`public_ratio` 是渠道对这一费用的公开倍率，不是模型单价。

两个渠道级倍率目前均默认 `1`，要求有限且大于零。修改上游倍率不应隐式修改用户价，修改公开倍率也不应隐式修改采购成本或 `floor` 排序。

## 3. 当前实际扣费与重试行为

普通模型费用的组合关系为：

```text
用户费用 = 按系统模型配置计算的费用
         × 生效分组倍率
         × 实际渠道 public_ratio
         × (1 + 生效服务费率)
```

- 用户专属分组倍率按原有优先级替代普通分组倍率，不将两者重复相乘。
- 服务费是最终费用中的组成部分，不是在最终扣费之外再收一遍。关闭服务费时费率按零处理。
- 工具附加费用沿用现有的倍率规则；违规罚金遵循原有独立规则，不套用上式追加服务费。
- 请求冻结服务费设置。重试换到另一个渠道时，按实际渠道更新公开倍率和预扣；需要更多预留时先补足，实际结算更便宜时返还差额，请求失败时按原有流程退款。
- 异步任务保留其计费快照；后续配置变化不能重算已经结算的历史费用。
- `upstream_ratio` 不在上述用户扣费公式中，采购成本也不会通过匿名目录或用户消费日志公开。

例如，假设一次按系统模型配置算出的费用为 1 美元、分组倍率为 2、渠道公开倍率为 1.2、服务费率为 5%，则组合费用为 2.52 美元。此例仅说明乘法关系，不代表任何模型的真实报价；实际 quota 换算与舍入仍由系统执行。

实现入口：`relay/helper/price.go`，以及 [最终计价说明](../../PROVIDERS.md#冒号路由与最终计价)。

## 4. 当前 `floor` 并不比较逐模型绝对采购价

当前 `floor` 按 `upstream_ratio` 从低到高选择渠道，同倍率档内沿用渠道权重，耗尽后再进入更高倍率档。`multiplier` 条件同样比较这个上游倍率，不比较公开倍率或用户费用。

以下为假设的单一输入用量示例，单位为美元/百万输入 token：

| 渠道 | 服务商倍率前输入价 | 上游倍率 | 折后采购价 |
| --- | ---: | ---: | ---: |
| A | 10 | 0.8 | 8 |
| B | 5 | 1.0 | 5 |

当前 `floor` 会优先 A，因为 `0.8 < 1.0`，但示例中的实际输入采购价是 B 更低。这正是“服务商倍率前价格不对齐”时，单一渠道倍率不足以表达成本的原因。**当前代码不会读取表中的倍率前价格，它们只是解释需求的假设值。**

同时，最低输入价不必然等于最低总成本：输出、缓存、按次收费和阶梯价格也可能不同。未来若要按真实采购成本路由，需明确比较口径，不能未经确认直接把 `floor` 改成按某一个单价排序。

## 5. 渠道评测与公开历史

- 定时任务和全量 `degradation-check` 扫描使用渠道凭据发起真实请求，可能产生上游费用；不进入本地用户 relay 扣费流程。打开服务商详情页面只是读取历史，**不会触发新评测或收费请求**。
- 已开始的评测返回正常、疑似降智、请求失败或取消结果后，按 UUID 独立追加；重复 UUID 不覆盖事实。取消或丢失任务租约时，仍尝试以每条最多 5 秒的独立写入上下文保存已返回结果，但不更新渠道快照、路由或任务进度。数据库写入失败会使任务失败，不承诺进程崩溃时能保存尚在内存中的结果。
- 未派发目标、被资格规则跳过的目标及 dry-run 不制造历史。独立 `degradation-probe --endpoint ...` 是不绑定渠道的无数据库诊断工具，不伪造服务商归属。
- 单模型定时检测在正常条件下将事实与快照同事务提交；全量扫描先存逐模型事实，仅在完整、未中断且租约/配置校验通过时发布渠道汇总。模型级事实不应被混称为渠道整体健康快照。
- `normal` 与 `abnormal` 都表示可调用，后者另外计为疑似降智。取消或无效目标/协议/代理/请求配置在公开统计中归为 `unknown`，不视为上游离线。

```text
检测可调用率 = online / (total - unknown)
```

没有可判定样本时不显示百分比；它是样本次数统计，不是连续在线时长或 SLA。

- 服务商详情支持近 7/30/90 天的 UTC 每日统计、每日 TTFT 曲线和范围内最新 50 条记录。TTFT 均值只使用可调用且实际测得首 token 的样本，按样本数计算全范围加权均值；0ms 是有效值，缺测不插值，也不使用总耗时替代 TTFT。
- 评测开始/完成、历史范围和每日桶使用 Unix **毫秒**；目录快照的 `last_checked_at` 使用 Unix **秒**。
- 历史不套用目录默认的最新在线/未降智筛选来隐藏过去的失败。公开可见性仍由主库的当前渠道状态、服务商状态和实例身份决定；复制、删除后重建及调整服务商归属不转移原身份的历史。
- 停用或删除不级联清理事实；历史当前没有默认过期清理任务。但未公开的渠道/服务商记录不能通过匿名接口读取。
- 公开响应不含 Key、Endpoint、原始回答/错误、映射后上游模型、上游采购成本或内部任务配置。检测开关与渠道路由启停相互独立。

参数、返回字段与统计口径见 [历史 API 说明](../../PROVIDERS.md#匿名历史查询与统计口径)。

## 6. ClickHouse 扩展边界

当前 `EvaluationHistoryStore` 将追加事实与时间范围读取同页面逻辑、主库授权查询解耦。当前运行环境以 PostgreSQL 为事实来源；关系库适配器仍兼容 SQLite/MySQL。

未来启用镜像时的计划链路是：

```text
主库事务：样本事实 + outbox（正常情况下还包括快照更新）
    → 提交
    → 后台认领待投递事件
    → 批量写入 ClickHouse
    → 确认投递；失败重试
```

- 此 outbox 和 ClickHouse 写入器**当前没有实现**，不应把修改 `SQL_DSN` 或消费日志库配置当作启用评测镜像的方法。
- 至少一次投递以样本 UUID 去重；晚到事实不能仅按评测开始时间或最大序号水位被跳过。
- `ReplacingMergeTree` 的最终合并不是即时唯一约束；查询和统计层必须避免重投事件重复计数，不能直接对未去重输入累加可调用率或均值。
- 读适配器切换前验证数据回填、同步积压和水位，不能把镜像延迟当成真实缺测或故障。
- 渠道/权限及未来价格配置仍由主库负责，不通过分析库的历史查询替代交易与授权边界。

完整扩展约定见 [ClickHouse 设计](../../PROVIDERS.md#后续-clickhouse异步镜像而非事务内双写)。

## 7. 渠道 × 模型独立定价：待确认事项

已登记的需求是：不同服务商在倍率前的价格可能不等于系统/官方参考价，需要对每个渠道的每个模型分别表达价格，而不是只使用一个渠道倍率。

以下内容尚未确定，不能假装已经生效：

1. **价格用途**：只记录上游采购基础价、只覆盖用户计费基础价，还是保存两套独立价格。
2. **计价维度与单位**：输入、输出、缓存读取/写入及缓存时长是否分别定价；按次/图像/其他用量如何表达；币种与单位必须明确。token 单价可考虑统一使用美元/百万 token，但这仍是候选约定。
3. **覆盖与回退**：逐渠道价格是否优先于系统模型价、部分字段缺省如何处理、如何兼容既有阶梯/表达式和管理员显式覆盖。不能把“未配置”与显式零价混为一谈；是否允许免费价需要明确。
4. **成本路由**：若保存采购价，是否调整 `floor`；输入与输出价格不同、预估与实际用量不同的情况下按什么规则比较。`multiplier` 的现有含义不能未经说明被改掉。

实现时必须保持的边界：

- 采购价与用户价分开命名、分开授权与公开投影；不能让成本字段自动进入匿名接口。
- 逐模型配置必须明确渠道身份、对外模型与上游映射的关系，不能误用厂商模型 ID 或给不同渠道共享一条可覆盖的单价记录。
- 实际采用的价格版本及倍率应进入请求/任务计费快照；修改配置、重试或延迟结算不能破坏预扣、补扣、退款及历史账单一致性。
- 遵守 [计费规则](../../.agents/rules/billing.md) 中的金额边界、quota 换算和管理员覆盖保护；不能产生负扣费、溢出返款或静默错价。
- 价格配置的迁移和查询需验证真实 SQLite/MySQL/PostgreSQL；补充未配置回退、部分覆盖、零/非法价格、模型映射、重试更换渠道、异步结算、隐私和权限回归。

**本文只记录现状与待决策边界，不新增价格字段、不调整 `floor`、不改变用户扣费。**
